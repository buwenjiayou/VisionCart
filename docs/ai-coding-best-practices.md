## 1. 核心理念

### AI 是助手，不是替代者

| 角色 | AI 擅长 | 人擅长的 |
|------|---------|---------|
| **执行者** | 重复性代码生成 | 理解业务需求 |
| **知识库** | 代码片段检索 | 判断是否正确 |
| **加速器** | 多轮快速迭代 | 架构设计决策 |
| **审查者** | 语法错误检查 | 逻辑漏洞发现 |

### 正确心态

```
❌ 错误：用 AI 替代思考
    "帮我写一个电商系统"

✅ 正确：用 AI 放大能力
    "在现有架构下，帮我实现商品搜索模块"
```

## 2. 上下文管理

### 2.1 上下文范围

AI 的上下文窗口有限，需要精打细算：

```
┌─────────────────────────────────────────┐
│           上下文窗口（有限）             │
├─────────────────────────────────────────┤
│                                         │
│  高优先级（必传）                         │
│  ├─ 当前任务的核心需求                   │
│  ├─ 相关代码片段（关键函数/类）          │
│  └─ 技术约束（框架版本、语言版本）        │
│                                         │
│  中优先级（按需）                         │
│  ├─ 项目架构概述                        │
│  ├─ 相关的 DTO/接口定义                 │
│  └─ 测试用例或预期行为                   │
│                                         │
│  低优先级（避免）                         │
│  ├─ 完整代码库（除非特别要求）           │
│  └─ 不相关的历史记录                    │
│                                         │
└─────────────────────────────────────────┘
```

### 2.2 上下文传递技巧

**技巧 1：先说背景，再提需求**

```
# ❌ 直接要代码
写一个用户登录接口

# ✅ 完整上下文
项目背景：
- Spring Boot 3.x + JPA
- 使用 JWT 认证
- 已有的 User 实体在 domain/user/User.java

需求：
- 实现邮箱+密码登录
- 返回 JWT token
- 密码需要 BCrypt 加密

约束：
- 不要用 Lombok
- 遵循现有 Repository 风格
```

**技巧 2：引用具体文件**

```
"参考 UserRepository.java 的实现风格，
写一个 ProductRepository"
```

**技巧 3：分块传递大需求**

```
# ❌ 一次说完
"帮我写一个完整的订单模块，包含：
- 实体、Repository、Service、Controller
- 订单创建、支付、退款流程
- 相关的 DTO 和异常处理"

# ✅ 分步骤
Step 1: "先帮我设计订单模块的数据库表结构"
Step 2: "基于表结构生成 JPA 实体"
Step 3: "实现 Repository 层"
...依次进行
```

### 2.3 上下文污染

**需要及时清理的情况：**

| 现象 | 解决方案 |
|------|---------|
| AI 开始生成不相关的代码 | 重新描述需求，明确范围 |
| 上下文越来越长但问题没解决 | 重新开一个会话 |
| AI 开始"编造"不存在的文件 | 停止，提供真实的代码片段 |

## 3. 约束边界设定

### 3.1 约束类型

```
┌──────────────────────────────────────────────────┐
│                    约束层次                        │
├──────────────────────────────────────────────────┤
│                                                  │
│  硬约束（必须遵守，违反会出错）                    │
│  ├─ 技术栈：Java 17 + Spring Boot 3.x             │
│  ├─ 代码规范：sonar 扫描通过                       │
│  └─ 安全要求：不暴露敏感信息                       │
│                                                  │
│  软约束（尽量遵守，提高代码质量）                   │
│  ├─ 命名规范：遵循现有风格                         │
│  ├─ 注释要求：公共方法加 Javadoc                   │
│  └─ 测试覆盖：核心逻辑有单元测试                   │
│                                                  │
│  灵活约束（可调整，视情况而定）                     │
│  ├─ 实现方式：可以用 Stream 或 for 循环           │
│  ├─ 代码位置：可以新建类或放现有类                 │
│  └─ 依赖选择：同功能的库选哪个都行                 │
│                                                  │
└──────────────────────────────────────────────────┘
```

### 3.2 约束表达方式

**方式 1：明确禁止**

```
"不要使用：
- @Slf4j（Lombok）
- MyBatis
- 全局异常处理器"

"禁止：
- 任何 SQL 字符串拼接（必须用参数化查询）
- 同步执行外部 API 调用"
```

**方式 2：明确要求**

```
"必须：
- 使用 RestClient（Spring 6.x 内置）
- 遵循现有的三层架构
- 返回 ApiResponse<T> 包装"
```

**方式 3：参考模板**

```
"参考现有的 ProductService 实现，
用同样的模式实现 OrderService"
```

### 3.3 约束验证

生成代码后，主动验证：

```
检查清单：
□ 技术栈是否正确？
□ 命名规范是否一致？
□ 是否引入了禁止的技术？
□ 是否遵循了项目约定？
```

## 4. 代码幻觉识别与调优

### 4.1 幻觉类型

| 类型 | 表现 | 危害 |
|------|------|------|
| **API 幻觉** | 使用不存在的 API、方法、参数 | 编译失败 |
| **逻辑幻觉** | 代码逻辑看似对但实际有 bug | 运行出错 |
| **版本幻觉** | 使用了新版才有的特性 | 兼容性失败 |
| **知识幻觉** | 给出错误的技术原理说明 | 误导理解 |

### 4.2 常见幻觉场景

**场景 1：编造 API**

```
AI 说："你可以用 StringUtils.isEmpty()"

实际情况：
- 可能是 apache.commons.lang3 的方法
- 也可能根本没有这个方法
- 应该用 jdk 自带的 isBlank() 或自己判断

✅ 验证方式：查官方文档或让 AI 给出方法来源
```

**场景 2：编造配置**

```
AI 说："在 application.yml 中添加：
spring.redis.host=localhost"

实际情况：
- 可能配置项名称不对
- 可能需要完整路径

✅ 验证方式：查看现有配置文件风格
```

**场景 3：编造文件路径**

```
AI 说："修改 config/DatabaseConfig.java"

实际情况：
- 文件可能在 config/database/ 目录下
- 可能根本不存在这个文件

✅ 验证方式：提供真实的文件路径或让 AI 先列出目录结构
```

### 4.3 调优策略

**策略 1：提供真实代码片段**

```
# ❌ 让 AI 猜测
"帮我修改用户认证的代码"

# ✅ 提供真实上下文
"这是我现有的 AuthController.java 第 15-30 行：
[粘贴代码]
请帮我添加一个新的登录方式：手机号+验证码"
```

**策略 2：要求 AI 解释再实现**

```
"在实现之前，请先：
1. 确认你使用的 Redis API 版本
2. 给出实现思路
3. 等我确认后再写代码"
```

**策略 3：分步验证**

```
# 每完成一步就验证
Step 1: "先生成 DTO，确认字段正确"
Step 2: "再生成 Service，确认逻辑正确"
Step 3: "最后生成 Controller"
```

**策略 4：指定知识来源**

```
"只使用 Spring Boot 6.x 官方文档中的 API，
不要使用第三方库的 API，除非我明确指定"
```

### 4.4 识别幻觉的信号

| 信号 | 含义 |
|------|------|
| AI 很"自信"地给出确定答案 | 可能是编造的 |
| 代码过于"完美" | 可能有隐藏问题 |
| 引用了很老的 API | 可能是过时知识 |
| 没有考虑边界情况 | 需要补充测试 |

## 5. 工具选择与组合

### 5.1 工具矩阵

| 工具 | 优势 | 劣势 | 最佳场景 |
|------|------|------|---------|
| **Cursor** | 深度代码理解、PR 上下文 | 上下文有限制 | 单文件修改、小功能实现 |
| **Trae (SOLO)** | 中文友好、多种工具集成 | 生态相对新 | 全栈开发、文档生成 |
| **GitHub Copilot** | IDE 集成、实时补全 | 缺乏项目全局理解 | 重复代码片段补全 |
| **Claude/GPT** | 通用对话、多模态 | 需要精确描述 | 架构设计、复杂逻辑讨论 |
| **MCP 工具** | 访问真实数据 | 需要配置 | 搜索代码库、读文件 |

### 5.2 工具组合使用

```
日常开发流程：

┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│   Cursor    │ →  │  Trae/SOLO  │ →  │   Claude    │
│             │    │             │    │             │
│ 单文件修改   │    │ 多文件生成   │    │ 架构设计    │
│ 实时补全    │    │ API 文档    │    │ 方案讨论    │
│ Bug 修复    │    │ 测试用例    │    │ 代码审查    │
└─────────────┘    └─────────────┘    └─────────────┘
```

### 5.3 场景推荐

| 需求 | 推荐工具 | 原因 |
|------|---------|------|
| 写一个工具方法 | Copilot / Cursor | 实时补全，快 |
| 重构一个模块 | Cursor + 选中代码 | 理解当前代码 |
| 设计新功能架构 | Claude / GPT | 通用推理能力强 |
| 生成 API 文档 | Trae/SOLO | 中文友好，格式规范 |
| 调试复杂 Bug | Claude + MCP 工具 | 可以读代码库 |
| 写测试用例 | Trae/SOLO | 生成完整文件 |

## 6. 典型工作流

### 6.1 小功能开发

```
1. 需求澄清（5分钟）
   └─ 明确：输入、输出、约束

2. AI 辅助实现（10分钟）
   └─ 分步骤生成，每步验证

3. 代码审查（5分钟）
   └─ 检查：逻辑、边界、安全

4. 测试验证（5分钟）
   └─ 编译运行，手动测试
```

### 6.2 中型模块开发

```
1. 架构设计（30分钟）
   └─ AI 讨论方案 → 确定架构

2. 分层实现（2小时）
   └─ Entity → Repository → Service → Controller
   └─ 每层完成后验证

3. 集成测试（30分钟）
   └─ 端到端测试

4. 文档补充（15分钟）
   └─ AI 生成 API 文档
```

### 6.3 Bug 修复流程

```
1. 复现问题
   └─ 确认 Bug 确实存在

2. 定位问题
   └─ 用 MCP 工具搜索相关代码

3. AI 分析原因
   └─ 提供错误信息和相关代码

4. AI 提出修复方案
   └─ 选择方案，手动修改（不要让 AI 直接改）

5. 验证修复
   └─ 测试确认问题解决
```

## 7. 常见误区

### 误区 1：期望 AI 一步到位

```
❌ "帮我写一个完整的电商系统"
   └─ 结果：代码量大、质量不可控

✅ "先帮我设计数据库表结构，我确认后再继续"
```

### 误区 2：不给约束

```
❌ "写一个用户服务"
   └─ 结果：可能用了你不熟悉的技术

✅ "用 Spring Boot 3.x、JPA、无 Lombok"
```

### 误区 3：不给上下文

```
❌ "这个接口报错怎么修"
   └─ 结果：AI 只能猜测

✅ 粘贴错误信息 + 相关代码 + 描述操作
```

### 误区 4：完全相信 AI

```
❌ AI 说什么就是什么
   └─ 结果：上线后出 Bug

✅ AI 生成的代码必须：
   - 自己 review
   - 编译通过
   - 测试通过
```

### 误区 5：不清理上下文

```
❌ 一个会话做 10 个不相关的任务
   └─ 结果：上下文混乱，AI 容易出错

✅ 每个任务开新会话
   或定期清理会话
```

### 模板 1：代码修改

```
## 背景
- 项目：xxx
- 技术栈：xxx
- 相关文件：xxx

## 需求
[描述要做什么]

## 约束
- [技术约束]
- [代码规范]
- [禁止项]

## 参考
[相关代码片段或文件路径]
```

### 模板 2：Bug 修复

```
## 错误信息
[粘贴完整错误信息]

## 相关代码
[粘贴相关代码片段]

## 操作步骤
[描述怎么操作导致报错]

## 已尝试的解决方式
[列出已尝试但无效的方法]
```

### 模板 3：架构设计

```
## 项目背景
[一句话描述项目]

## 需求描述
[详细描述要解决的问题]

## 约束条件
- 性能要求
- 技术限制
- 时间限制

## 请先分析
1. 可能的方案有哪些？
2. 各方案的优缺点？
3. 推荐方案及理由？

[等 AI 回答后，再决定是否继续深入]
```

## 总结

| 原则 | 说明 |
|------|------|
| **AI 是助手** | 放大能力，不是替代思考 |
| **上下文为王** | 给的上下文决定输出质量 |
| **约束要明确** | 减少 AI 猜测，降低幻觉 |
| **验证不可少** | 生成的代码必须 review |
| **工具要组合** | 不同场景用不同工具 |
| **定期沉淀** | 把经验变成模板和流程 |
