# VisionCart AI Coding 心得沉淀：高效使用 AI 辅助编码

## 1. 项目背景与 AI Coding 使用目标

VisionCart 是一个 AI 智能比价购物助手，包含 Android 客户端和 Spring Boot 后端。用户通过拍照或上传商品图片触发识别，后端调用视觉模型提取商品属性，再从拼多多、淘宝联盟、eBay 等平台检索商品，最终完成跨平台比价、筛选、收藏、历史记录和价格提醒。

这个项目的复杂度不只在于“代码量”，更在于它同时涉及移动端体验、后端接口、数据库持久化、Redis 缓存、第三方电商接口、AI 模型调用、自然语言理解和安全合规。开发过程中，如果只把 AI 当成代码补全工具，很容易得到一些看起来完整、但无法接入真实项目的代码。因此，我们在 VisionCart 中对 AI Coding 的定位是：让 AI 提升开发效率，但不让 AI 替代工程判断。

具体来说，AI 在项目中的作用主要有四类：

1. 辅助需求拆解：把“拍照识别并比价”拆成图片上传、异步识别、属性结构化、多平台检索、结果排序、前端展示等可实现任务。
2. 辅助代码生成：根据已有模块风格生成 DTO、Service、Controller、Compose 组件、测试样例等重复性代码。
3. 辅助调试排查：结合编译错误、接口响应、后端日志、Android Logcat 信息分析问题原因。
4. 辅助文档沉淀：把开发过程中的架构决策、使用流程、接口说明、测试经验整理为可复用文档。

在这个过程中，我们逐渐形成了一套适合两人团队开发的 AI Coding 方法：先给真实上下文，再设置明确边界；先让 AI 给方案，再让 AI 写代码；先小步生成，再通过编译、测试、日志和人工审查不断纠偏。

## 2. AI Coding 在 VisionCart 中的实际使用场景

### 2.1 后端模块搭建

后端采用 Spring Boot 3.5 + Java 17，整体结构包括 Controller、DTO、Service、Repository、Domain 和 Config。AI 在后端开发中最适合承担“模式化代码生成”和“方案对比”工作。例如新增接口时，我们会先告诉 AI 项目统一返回 `ApiResponse<T>`，Controller 层只做参数校验和权限判断，业务逻辑必须进入 Service 层，数据访问必须通过 Repository。

以识别模块为例，AI 可以辅助梳理 `RecognitionController`、`RecognitionOrchestrator`、`VisionModelService`、`ImageProcessor` 的职责划分：Controller 接收图片并返回 sessionId，Orchestrator 负责编排异步任务，VisionModelService 封装模型调用，ImageProcessor 处理图片压缩和格式校验。这样 AI 输出的代码会更贴近项目分层，而不是把所有逻辑塞进一个接口方法里。

### 2.2 Android UI 与数据层开发

Android 端使用 Kotlin、Jetpack Compose、CameraX、Room、DataStore 和 Retrofit。AI 在移动端开发中的价值主要体现在 UI 状态建模、数据流整理和边界状态补全。例如围绕 `MainViewModel` 和 `VisionCartRepository`，AI 可以帮助分析识别中、识别成功、识别失败、搜索中、搜索结果为空、收藏同步失败等状态如何呈现在 Compose UI 中。

不过，Android 端也更容易出现 AI 幻觉。比如 AI 可能会假设某个 Compose 组件已经存在，或者把网络请求直接写在 UI 层。我们的纠偏方式是明确告诉 AI：Repository 是数据单一入口，TokenManager 负责 JWT 持久化，OkHttp Interceptor 负责自动携带 token，UI 只消费 ViewModel 暴露的状态。

### 2.3 接口联调与错误排查

项目涉及 Android 与后端联调，常见问题包括 Base URL 配置错误、JWT 未携带、请求字段命名不一致、图片上传格式错误、后端返回结构与 Android data class 不匹配等。AI 在这里适合做“错误归因助手”。

例如遇到 Android 请求失败时，我们不会只给 AI 一句“接口报错了”，而是同时提供：

- Retrofit 接口定义
- 请求 URL 和状态码
- 后端 Controller 方法
- 后端日志关键行
- Android 端 data class
- 预期返回的 JSON 结构

这样 AI 才能判断是网络地址问题、鉴权问题、字段映射问题，还是后端业务异常。

### 2.4 文档整理与验收材料

VisionCart 包含较多工程能力：异步识别、多平台检索、NLP 筛选、价格提醒、收藏历史、Redis 缓存、WebSocket 推送等。AI 很适合把这些内容整理为 README、部署说明、API 使用说明和项目总结。但文档生成同样不能完全信任 AI，必须回到真实代码核对类名、接口路径和配置项。

### 2.5 两人团队中的 AI 协作方式

我们是两人团队，因此 AI Coding 的价值不只是提高单人编码速度，也帮助我们降低协作成本。实际开发中，我们会把任务拆成相对清晰的边界：一侧更关注后端接口、AI 服务、多平台搜索和数据持久化，另一侧更关注 Android 交互、状态管理、本地缓存和联调体验。

AI 生成的方案不会直接默认通过，而是进入团队内的二次确认：涉及接口契约、数据库字段、鉴权和敏感配置的内容，需要另一名成员从兼容性和安全角度再看一遍；涉及 Android UI、状态流和用户操作路径的内容，也需要结合真机或模拟器体验确认。这样可以避免两个人分别使用 AI 后产生不一致的字段、路径或实现风格。

我们也会把反复达成共识的内容沉淀到项目文档中，例如接口返回格式、敏感信息规则、目录边界、测试命令和验收标准。这样 AI 不只是临时助手，也逐渐成为团队协作流程的一部分。

## 3. 高效使用 AI 的核心流程

我们总结的高效流程可以概括为：任务定义、上下文投喂、边界约束、分步生成、工程验证、经验沉淀。

### 3.1 任务定义：把“大需求”拆成“小闭环”

不建议直接问 AI：

```text
请实现一个 AI 比价购物助手。
```

这样的请求太大，AI 会倾向于重新设计项目，产出的内容无法直接合并。更好的方式是把需求拆成可以验证的小闭环：

```text
在现有 Spring Boot 后端中，基于 RecognitionOrchestrator 的异步识别流程，
请分析识别任务从上传图片到返回结果的状态流，并指出 Controller、Service、DTO 各自需要承担的职责。
暂时不要写代码，先给方案和风险点。
```

这样 AI 会先对齐项目现状，再进入实现。

### 3.2 上下文投喂：只给和当前任务有关的信息

AI 的上下文窗口有限，而且上下文越混乱，幻觉越多。我们的做法是按照优先级投喂上下文：

- 必须提供：当前任务目标、相关类、接口契约、错误日志、技术栈版本。
- 按需提供：相邻模块实现、测试文件、配置片段、数据库实体。
- 尽量不提供：完整仓库、无关历史对话、长日志、过时方案。

例如处理 NLP 筛选时，我们会优先提供 `RuleBasedNlpParser`、`SpringAiNlpService`、`PromptLoader`、`PromptSanitizer`、`AiOutputValidator` 的职责，而不是把整个后端目录都交给 AI。

### 3.3 边界约束：告诉 AI 什么不能做

AI 很擅长“补全”，但不擅长自动遵守项目隐含约束。因此每次让 AI 参与实现时，我们都会明确写出边界：

```text
约束：
1. 后端使用 Java 17 + Spring Boot，不引入 MyBatis。
2. Controller 必须返回 ApiResponse<T>。
3. 敏感配置只能来自 application.yml 的环境变量占位符，不要写死密钥。
4. 不要修改 Android 端已有数据模型，除非明确说明兼容方案。
5. 先列出将修改的文件和原因，再给代码。
```

这类约束能显著降低 AI 自作主张新增依赖、改目录、重写接口的概率。

### 3.4 分步生成：先方案，后代码，再测试

复杂任务我们通常分三轮让 AI 参与：

第一轮只问方案：让 AI 说明实现思路、影响范围、潜在风险。

第二轮再生成代码：只让它处理 1 到 3 个相关文件，避免一次性大改。

第三轮让 AI 根据编译结果或测试失败信息修正。

这种流程看似多了一步，但实际更快，因为它避免了 AI 一次性生成大量不符合项目约束的代码。

### 3.5 先定义验收标准，再让 AI 动手

参考一些优秀的 AI Coding 经验后，我们发现高质量协作通常不是从“请直接写代码”开始，而是从“什么算完成”开始。也就是说，先写清楚完成标准，再让 AI 生成方案和代码。

在 VisionCart 中，我们会把验收标准写得尽量可验证。例如：

```text
完成标准：
1. 后端接口返回结构不变，仍然使用 ApiResponse<T>。
2. Android 端现有 data class 不需要破坏性修改。
3. 搜索失败时不能影响识别历史保存。
4. 至少补充一个平台失败但整体搜索成功的测试。
5. 运行相关 Gradle 测试通过。
```

这类标准能把 AI 的注意力从“生成一段代码”转向“交付一个可验证结果”。如果没有完成标准，AI 很容易停留在“看起来完成”的状态；有了完成标准，后续编译、测试、文档核验才有依据。

## 4. 上下文管理实践

VisionCart 是 Android + 后端多模块项目，上下文管理尤其关键。我们主要采用“项目级上下文 + 模块级上下文 + 当前问题上下文”的三层管理方式。

### 4.1 项目级上下文

项目级上下文用于让 AI 理解整体工程边界，例如：

- VisionCart 是 AI 智能比价购物助手。
- 后端是 Spring Boot，Android 是 Kotlin + Compose。
- 后端统一使用 `ApiResponse<T>` 返回。
- 敏感信息只放后端环境变量。
- Android 通过 `local.properties` 注入 API Base URL。
- 收藏和识别历史需要本地缓存并与后端同步。

这些信息适合放在 AGENTS.md、README 或固定 Prompt 中，作为每次 AI 会话的基础约束。

### 4.2 模块级上下文

模块级上下文用于减少 AI 对架构的误判。例如：

- 识别模块：`RecognitionOrchestrator` 负责编排，`VisionModelService` 负责模型调用，`ImageProcessor` 负责图片处理。
- 搜索模块：`SearchOrchestrator` 统一编排，`PlatformSearchService` 是平台适配接口，`PlatformCircuitBreaker` 负责熔断。
- NLP 模块：`RuleBasedNlpParser` 规则优先，`SpringAiNlpService` 负责 LLM 兜底，`AiOutputValidator` 校验输出。
- Android 数据层：`VisionCartRepository` 是数据入口，`MainViewModel` 管理 UI 状态。

有了模块级上下文，AI 就更容易在现有结构中补代码，而不是重新发明一套结构。

### 4.3 当前问题上下文

当前问题上下文必须具体。例如要修复搜索结果排序异常，就应提供：

- 当前输入的商品属性和筛选条件
- 搜索返回的商品列表样例
- 期望排序规则
- 当前排序相关代码
- 单元测试或手动复现步骤

我们发现，AI 对“具体输入 + 具体输出 + 具体代码”的响应质量远高于对抽象描述的响应质量。

## 5. 约束边界设定实践

### 5.1 技术栈边界

在项目中，我们会明确限制 AI 不要随意引入新技术。后端固定使用 Spring Boot、Spring Security、Spring Data JPA、Redis、MySQL、Micrometer；Android 固定使用 Kotlin、Compose、CameraX、Room、DataStore、Retrofit。除非确实能降低复杂度，否则不接受 AI 建议的额外依赖。

这样做的原因是：AI 往往会为了快速解决局部问题引入一个库，但真实项目中依赖越多，构建、维护、安全审查和团队理解成本越高。

### 5.2 目录边界

后端目录边界：

- `api/controller`：REST 接口入口。
- `api/dto`：请求和响应 DTO。
- `service`：业务逻辑。
- `domain`：JPA 实体。
- `repository`：数据库访问。
- `config`：安全、JWT、WebSocket、OpenAPI、配置属性。

Android 目录边界：

- `data`：API、模型、Token、Room。
- `data/repository`：统一数据入口。
- `ui`：Compose 页面和组件。
- `overlay`：悬浮窗服务。

当 AI 生成代码偏离这些目录时，即使代码本身能编译，我们也会要求它改回项目结构。

### 5.3 接口契约边界

后端接口必须遵守统一响应结构，Android data class 必须与后端 JSON 命名策略保持一致。尤其是后端 Jackson 使用 `SNAKE_CASE`，Android 端字段映射需要稳定。如果 AI 修改 DTO 字段，必须同步评估：

- 后端 Controller 返回是否变化。
- Android Retrofit 模型是否兼容。
- 已有测试是否需要更新。
- 老数据或本地缓存是否受影响。

### 5.4 安全边界

AI 不能接触或输出真实密钥。VisionCart 涉及模型 API、电商平台 API、数据库、Redis、邮件服务等配置，所有敏感信息都应放在 `.env` 或服务器环境变量中。让 AI 写示例时，只能使用类似 `<ARK_API_KEY>` 的占位符，不能粘贴真实值。

此外，AI 模型调用本身也要有安全边界。NLP 模块中，用户输入先经过 `PromptSanitizer` 检测提示词注入，再通过 `AiOutputValidator` 校验 LLM 输出字段，避免模型返回超范围平台、非法排序字段或不可信条件。

## 6. 代码幻觉识别与纠偏

AI Coding 最大的风险不是“写错语法”，而是“自信地写出不符合真实项目的内容”。我们在项目中遇到或重点防范的幻觉主要有以下几类。

### 6.1 API 幻觉

表现：AI 调用不存在的方法、错误的 Spring 配置项、旧版本 Android API，或者把第三方平台接口字段想当然统一。

纠偏方式：

- 让 AI 标注 API 来源。
- 用 IDE 跳转和编译验证。
- 对第三方接口以官方文档和真实响应为准。
- 对平台适配层增加单元测试，固定输入输出。

### 6.2 路径幻觉

表现：AI 建议修改不存在的文件，例如凭空出现 `DatabaseConfig.java`、`ProductService.kt`，或把后端 DTO 放到 Android 目录。

纠偏方式：

- 先让 AI 基于真实目录树工作。
- 提示“只能修改这些文件”。
- 让 AI 输出修改清单，再开始代码生成。

### 6.3 业务幻觉

表现：AI 假设所有平台都有销量、评分、佣金、原价、店铺信誉等字段；或者假设图片识别一定能返回品牌、颜色、材质等完整属性。

纠偏方式：

- 明确第三方数据可能缺失。
- DTO 字段设计允许为空。
- 排序和筛选逻辑必须考虑字段缺失。
- 搜索结果为空时要有降级策略。

### 6.4 过度设计

表现：AI 为了显得架构完整，新增过多抽象、工厂、策略类或配置层，导致简单功能复杂化。

纠偏方式：

- 要求 AI 给出“最小可用实现”。
- 问清新增抽象解决了什么重复或复杂度。
- 如果只服务一个场景，优先放在现有 Service 中。

### 6.5 纠偏 Prompt 示例

```text
你刚才的方案里出现了不存在的文件和未验证的 API。
请重新基于以下真实上下文回答：
1. 只能使用我们列出的类和路径。
2. 不要新增依赖。
3. 如果某个方法或配置项不确定，请明确标注“不确定”，不要编造。
4. 先给修改范围和原因，不要直接输出代码。
```

这种提示能把 AI 从“继续编”拉回“基于事实推理”。

### 6.6 让 AI 主动列出不确定项

不少 AI 辅助编码经验都强调一点：不要逼 AI 给出确定答案，而要允许它承认不确定。实际开发中，如果模型不知道某个类是否存在、某个第三方 API 字段是否可用、某个配置项是否支持，它仍然可能为了完成回答而编造。

因此我们会在复杂任务里加一句：

```text
如果你无法从当前上下文确认某个事实，请列入“不确定项”，不要假设它存在。
```

这个小约束非常有用。它能把 AI 的输出从“自信生成”变成“事实、推断、不确定项分离”。在 VisionCart 这种涉及电商平台接口和 AI 模型服务的项目中，不确定项尤其重要，因为平台字段、模型返回、网络错误和环境配置都可能与理想情况不同。

## 7. Cursor、Trae、Claude Code、Codex 等 AI Coding 工具的使用思路

查阅 Cursor、Trae、Claude Code、Codex 的资料后，我们更认可“按研发阶段选择工具”，而不是简单比较哪个工具更强。需求澄清阶段，适合用 Trae、Claude Code 或 Codex 先拆任务、看调用链、写计划；局部编码阶段，Cursor 和 Trae Inline Chat 更高效；跨文件执行和验证阶段，Claude Code 与 Codex 更适合读仓库、跑测试、总结风险。

Cursor 的优势是贴近编辑器，适合基于选中代码做解释、重构、补测试和小范围修改。使用时我们会尽量引用具体文件或代码片段，例如只分析 `SearchOrchestrator` 的分页逻辑，就不让它读取整个 `service/search`。Cursor 的 Project Rules 也适合沉淀高频约束，例如“后端必须返回 `ApiResponse<T>`”“Android 不保存密钥”“搜索逻辑要考虑字段缺失”。

Trae 更适合中文需求拆解和多文件生成。比如“新增价格提醒”“优化悬浮窗截图识别”“整理验收文档”这类需求，可以先让 Trae Builder 读项目、拆任务、列出文件清单，再逐步生成。使用 Trae 时要控制变更节奏：优先给 `#Code` 或 `#File`，跨模块时再使用 `#Workspace`；每轮生成后先看 diff，再决定 Accept、Reject 或 Revert。

Claude Code 更像终端里的工程协作者，适合计划优先和复杂链路排查。它适合处理“读代码、跑命令、跨文件推理”的任务，例如梳理 Android 拍照到后端识别结果返回的完整链路。我们的使用方式是先让它进入计划模式，只读代码、列风险、给修改计划，再决定是否执行；长期规则则沉淀到 `CLAUDE.md`。

Codex 更适合仓库级闭环任务，尤其适合“计划、实现、验证、审查”连在一起的工作。VisionCart 的 `AGENTS.md` 已经记录了项目结构、构建命令和安全规则，因此使用 Codex 时可以把任务写成 Goal、Context、Constraints、Done when 四部分。Codex 还能在实现后从 review 视角检查回归风险、缺失测试和接口兼容性。

总结下来，编辑器内工具负责快，agent 工具负责稳。无论使用哪个工具，都要先给边界、再给上下文、最后用测试和日志验证。AI 工具之间不是替代关系，而是共同服务于一条工程闭环：计划、实现、验证、审查、沉淀。

## 8. AI 工具创新应用案例

### 8.1 异步识别流程设计

最初如果按直觉实现图片识别，很容易写成同步接口：客户端上传图片，后端调用视觉模型，等待模型返回后再响应。这个方案简单，但对移动端体验不好，因为模型调用和多平台搜索都可能耗时。

我们借助 AI 讨论后，将流程调整为异步模式：

1. Android 上传图片。
2. 后端返回 `sessionId`。
3. `RecognitionOrchestrator` 后台执行图片处理、模型识别和搜索。
4. 客户端通过 `/api/v1/recognition/status/{sessionId}` 轮询。
5. 有条件时通过 WebSocket 推送识别进度和结果。

这个案例中，AI 的价值不是直接生成全部代码，而是帮助比较同步和异步的体验差异、状态流复杂度和异常处理方式。

### 8.2 多平台搜索与熔断降级

VisionCart 同时对接多个电商平台，不同平台的稳定性、字段完整度和响应速度都不一样。AI 辅助我们梳理了几个关键问题：

- 平台接口是否并行调用。
- 某个平台失败时是否影响整体搜索。
- 搜索结果如何统一成 `ProductCard`。
- 缓存命中时是否还需要写入 session 级候选池。
- 熔断打开后如何跳过异常平台。

最终项目通过 `SearchOrchestrator` 编排多个 `PlatformSearchService`，并使用 `PlatformCircuitBreaker` 降低外部服务异常对整体体验的影响。AI 在这里提供的是方案推演和边界场景补充，最终实现仍要用测试和日志验证。

### 8.3 NLP 规则优先与 LLM 兜底

自然语言筛选如果完全依赖 LLM，成本和不确定性都会较高；如果完全使用规则，又难以覆盖复杂表达。AI 辅助我们形成了混合方案：

- 高频条件走 `RuleBasedNlpParser`，例如价格区间、平台、颜色、评分、销量、排序。
- 规则不完整时再调用 `SpringAiNlpService`。
- Prompt 模板通过 `PromptLoader` 管理。
- 用户输入先经过 `PromptSanitizer`。
- LLM 输出再经过 `AiOutputValidator`。
- 调用耗时和结果通过 `AiTraceService` 观测。

这个设计体现了 AI 应用中的一个重要原则：LLM 不应该直接控制业务结果，必须经过规则约束、结构化解析和业务校验。

### 8.4 用 AI 做测试设计

AI 很适合从已有逻辑中推导测试场景。例如搜索模块可以让 AI 列出：

- 平台全部成功。
- 单个平台失败。
- 搜索结果为空。
- 缓存命中。
- 熔断打开。
- 筛选条件缺失。
- 排序字段异常。

但测试代码不能只看 AI 生成是否漂亮，还要看断言是否真的覆盖风险。例如只断言“不为空”的测试价值很低，应该断言排序顺序、过滤条件、错误分支、缓存写入或降级行为。

### 8.5 用 AI 做项目文档沉淀

在项目后期，AI 对文档整理非常有用。它可以把模块实现、接口流程、调试经验、验收用例整理成结构化材料。但文档必须经过事实校验，尤其是类名、接口路径、配置项、环境变量和测试命令。否则 AI 可能写出“项目看起来应该有”的文档，而不是“项目实际拥有”的文档。

## 9. AI 编码调优实践

### 9.1 Prompt 从“命令式”改为“协作式”

低质量 Prompt：

```text
请写搜索功能。
```

高质量 Prompt：

```text
背景：这是一个 Spring Boot 后端，搜索入口是 SearchController，
核心编排类是 SearchOrchestrator，平台服务实现 PlatformSearchService。

任务：请分析如何在不改变现有接口返回结构的前提下，为搜索结果增加一个排序策略。

约束：
1. 不新增外部依赖。
2. 不修改 Android 接口字段。
3. 先给方案和影响范围，不要直接写代码。
```

协作式 Prompt 能让 AI 先理解上下文和边界，再进入实现。

### 9.2 用“反向审查”提升质量

AI 写完方案后，我们会继续追问：

```text
请从代码审查角度检查你的方案，重点找：
1. 是否破坏现有接口兼容性。
2. 是否有空指针或字段缺失风险。
3. 是否引入安全问题。
4. 是否需要新增测试。
```

这一步能逼 AI 从“生成者”切换成“审查者”，经常能发现第一轮没有考虑到的问题。

### 9.3 用编译和测试结果驱动迭代

AI 的输出必须进入真实工程验证。后端至少要通过 Gradle 编译和相关单元测试；Android 至少要关注编译、关键 ViewModel 测试、UI 状态是否符合预期。

当测试失败时，给 AI 的信息应该包含：

- 失败命令。
- 完整错误摘要。
- 相关代码片段。
- 期望行为。
- 最近一次修改内容。

这样 AI 才能定位问题，而不是继续猜。

### 9.4 把可复用经验固化为规则

随着项目推进，我们会把反复出现的要求沉淀为固定规则，例如：

- 后端接口返回 `ApiResponse<T>`。
- JSON 使用 `SNAKE_CASE`。
- Android 不保存任何平台密钥。
- 外部 API 调用必须考虑超时、失败和降级。
- LLM 输出必须经过结构化校验。
- 涉及多文件修改时先列计划。

这些规则写入项目文档后，后续 AI 会话可以复用，减少重复沟通成本。

### 9.5 调优补充：reviewer、事实分离与分层推进

参考一些团队使用 AI 的经验后，我们会在复杂任务中先让 AI 做 reviewer，再让它做 coder。也就是说，先让它指出可能影响的接口、回归风险、安全风险和最小测试集合，再进入实现。这样可以避免 AI 直接“补代码”，却忽略 Android 本地缓存、后端 DTO、接口兼容或用户体验。

排查问题时，我们还会要求 AI 把输出拆成“事实、推断、建议、不确定项”。事实必须来自代码或日志，推断要说明依据，不确定项不能包装成结论。这个结构能减少幻觉，也方便决定下一步是读代码、跑测试还是补充上下文。

另外，不让 AI 一次性跨太多层。涉及 Android + 后端 + 数据库 + 文档的任务，我们会按层推进：先确认接口和 DTO，再实现 Service/Repository，再补测试，再更新 Android，最后整理文档。每层都能独立验证，整体成功率会比一次生成全栈代码更高。

## 10. AI Coding 常用检查清单

### 10.1 开始编码前

- 是否明确当前任务的输入、输出和成功标准。
- 是否知道要修改哪些模块。
- 是否给了 AI 真实类名和路径。
- 是否说明了不能引入的新依赖。
- 是否说明了接口兼容要求。
- 是否明确安全边界。

### 10.2 AI 输出代码后

- 类名、方法名、路径是否真实存在。
- 是否符合项目目录结构。
- 是否破坏已有 DTO 或接口返回。
- 是否有空值、异常、超时和失败分支处理。
- 是否把密钥、token、账号写进代码或文档。
- 是否需要补测试。

### 10.3 合并前

- 后端是否能编译。
- Android 是否能编译。
- 关键单元测试是否通过。
- 接口响应是否与 Android 模型匹配。
- 文档是否与真实实现一致。
- 是否留下临时日志、测试数据或调试配置。

## 11. 团队收获与方法论总结

通过 VisionCart 项目，我们对 AI Coding 的理解从“让 AI 写代码”转变为“用 AI 加速工程闭环”。AI 的优势是速度快、知识面广、能快速给出多个方案；但它的弱点也很明显：容易脱离上下文，容易编造不存在的 API，容易忽略项目约束，容易低估联调和边界场景。

因此，高效使用 AI 的关键不是问得更多，而是问得更准。一个好的 AI Coding 请求应该包含背景、目标、上下文、约束、输出格式和验证方式。一个好的 AI Coding 流程应该包含人工决策、AI 生成、工程验证和经验沉淀。

在 VisionCart 中，AI 帮助我们更快完成了后端模块搭建、Android 状态流梳理、AI 模型调用封装、多平台搜索设计、NLP 筛选方案、测试场景补充和文档总结。但最终真正保证项目质量的，仍然是对架构边界的坚持、对真实代码的核验、对安全问题的警惕，以及通过编译、测试、日志、接口联调形成的验证闭环。

后续如果继续优化 AI Coding 流程，我们会重点做三件事：

1. 建立项目专属 Prompt 模板，把常见任务如新增接口、补测试、排查错误、写文档标准化。
2. 建立幻觉案例库，记录 AI 常见错误和对应纠偏方式。
3. 建立 AI 生成代码验收清单，让每次 AI 输出都经过统一检查。

总体来说，AI Coding 不是降低工程要求，而是提高工程节奏。只有把 AI 放在真实上下文、清晰边界和严格验证之中，它才能从“会聊天的代码生成器”变成真正有价值的开发协作工具。
