# 团队AI Coding 心得

## 1. 前言

VisionCart 是我们两个人一起完成的 AI 智能比价购物助手，项目里同时有 Android 客户端、Spring Boot 后端、视觉模型识别、自然语言筛选、多平台商品搜索、收藏历史和价格提醒。刚开始我们对 AI Coding 的期待比较直接：让 AI 帮我们快点写代码。真正做下来以后才发现，AI 最有价值的地方不是“替我们写完整项目”，而是帮助我们更快拆需求、读代码、补样板、排查错误和整理文档。

这个项目里也出现过几次明显的 AI 幻觉：它会假设不存在的 Compose 组件，会把后端接口字段想当然同步到 Android，会用一个看起来合理但项目里没有的配置类，也会把 PDD、淘宝联盟、eBay 的字段当成完全一致。后来我们固定下来一个习惯：AI 只负责加速，最终判断必须回到真实代码、接口返回、日志和测试。

## 2. 我们团队怎么分工使用 AI

我们是两人团队，所以 AI Coding 不只是单人提效，也影响两个人之间的协作方式。实际开发中，我们大致按模块分工：一侧更多处理后端接口、AI 服务、多平台搜索、数据持久化；另一侧更多处理 Android 页面、状态管理、本地缓存和前后端联调。

AI 生成的内容不会直接当作最终方案。涉及接口契约、数据库字段、鉴权、环境变量和敏感配置时，会由另一名成员再看一遍；涉及 Android UI、ViewModel 状态和用户操作路径时，也会结合真机或模拟器体验检查。这个“二次确认”很重要，因为两个人分别使用 AI 时，很容易产生字段名、接口路径、异常处理方式不一致的问题。

我们后期把反复达成共识的规则沉淀到项目文档里，例如：

- 后端接口统一返回 `ApiResponse<T>`。
- 后端 JSON 使用 `SNAKE_CASE`。
- 密钥只放后端 `.env` 或服务端环境变量。
- Android 不保存任何模型或平台密钥。
- 多平台搜索要考虑超时、空结果、字段缺失和降级。
- AI 生成的类名、路径、接口都要回到仓库里验证。

这些规则让 AI 不再只是临时聊天工具，而是进入了我们的团队协作流程。

## 3. 高效使用 AI 的流程

我们后来稳定下来的流程是：先拆任务，再给上下文，再设约束，最后用测试和日志纠偏。

一开始我们试过直接让 AI “实现图片识别并比价”。这种问法太大，AI 很容易重新设计一套项目结构，生成的代码看起来完整，但接不进现有 Android 和后端。后来我们改成小闭环提问，例如：

```text
请先阅读 RecognitionController、RecognitionOrchestrator 和 Android 调用处，
只分析图片上传后 sessionId、轮询、WebSocket 推送的状态流。
先给风险和修改点，不要直接写代码。
```

这种方式更稳。AI 会先对齐现有代码，再围绕当前链路给建议。

### 3.1 上下文管理

我们不会把整个项目都丢给 AI，而是分层给上下文。

项目级上下文主要是固定规则：VisionCart 是 Android + Spring Boot 项目，后端统一返回 `ApiResponse<T>`，敏感信息只在后端环境变量中，Android 通过 `local.properties` 配置 API 地址。

模块级上下文是当前任务相关的类。例如处理识别链路时给 `RecognitionOrchestrator`；处理搜索时给 `SearchOrchestrator`、`PlatformSearchService`、`PlatformCircuitBreaker`；处理 NLP 时给 `RuleBasedNlpParser`、`SpringAiNlpService`、`PromptSanitizer`、`AiOutputValidator`；处理 Android 状态时给 `MainViewModel` 和 `VisionCartRepository`。

问题级上下文必须具体。比如接口联调失败时，我们会同时给 Retrofit 定义、请求状态码、后端 Controller、关键日志和期望 JSON，而不是只说“接口报错了”。这个坑出现过几次：上下文不够时，AI 会优先猜网络、猜权限、猜字段，结果越改越偏。

### 3.2 约束边界

AI 很擅长补全，但不擅长自动遵守项目边界。所以我们每次让 AI 参与实现时，都会把约束写清楚：

```text
约束：
1. 不新增外部依赖。
2. 不修改已有接口字段，除非说明 Android 兼容方案。
3. 后端 Controller 必须返回 ApiResponse<T>。
4. 敏感配置只能使用环境变量占位符。
5. 先列出会修改的文件和原因，再生成代码。
```

这个习惯帮我们挡住了不少问题。比如 AI 曾建议把某些搜索配置写进 Android，或者为了一个小筛选逻辑新增复杂策略类。我们最后都要求它回到后端配置、现有 Service 分层和最小实现。

### 3.3 完成标准前置

参考官方文档和一些公开 AI Coding 实践后，我们也把“完成标准”放到了提问前面。比如搜索逻辑改动，我们会先写：

```text
完成标准：
1. 后端接口返回结构不变。
2. PDD/Taobao/eBay 任一平台失败时，整体搜索仍能返回可用结果。
3. Android 现有数据模型不破坏。
4. 至少补一个平台失败的测试。
5. 相关 Gradle 测试通过。
```

这样 AI 不会只追求“代码写出来”，而会围绕能不能验收来工作。

## 4. AI 工具使用心得

我们用过的工具里，Trae、Codex、Claude Code 和 Cursor 的分工最清楚。

Trae 更适合中文需求拆解。比如“价格提醒”“悬浮窗截图识别”“AI 使用总结”这种需求，我们会先让 Trae 帮忙拆成后端实体、接口、Android 状态、UI 和测试几部分。Trae Builder 做多文件任务很方便，但我们不会直接全量接受它的改动，而是先看文件清单和 diff，确认没有顺手改到无关模块。

Codex 更适合仓库级闭环任务。VisionCart 有 `AGENTS.md`，里面记录了项目结构、构建命令和安全规则，所以 Codex 能比较快进入项目上下文。我们一般给 Codex 的任务会写成 Goal、Context、Constraints、Done when。比如这份文档就是典型的 Codex 任务：只改 `docs/AI_CODING_REFLECTION.md`，不能碰 `.env`，不能包含真实密钥，最后要检查标题、关键词和敏感信息。

Claude Code 更适合复杂链路排查。比如异步识别、搜索排序、候选池缓存这类跨文件逻辑，我们会让它先进入计划模式，只读代码、画调用链、列风险，再决定是否执行。`CLAUDE.md` 适合存放 Claude Code 的长期规则，例如“先计划后修改”“测试失败先总结根因”“不要自动执行危险命令”。

Cursor 更适合局部编辑。比如选中一个 ViewModel 方法、一个 Controller 或一段排序代码，让它解释、重构或补测试。Cursor 的优势是快，但我们不会让它在不明确范围的情况下扫全仓库。

总结下来，编辑器内工具负责快，agent 工具负责稳。Trae 偏需求拆解，Codex 偏执行闭环，Claude Code 偏复杂排查，Cursor 偏局部修改。工具之间不是替代关系，而是按阶段组合。

## 5. 代码幻觉与纠偏

我们在项目里主要遇到四类幻觉。

第一类是 API 幻觉。AI 会使用不存在的方法、错误的配置项，或者把不同平台商品字段当成统一字段。多平台搜索里这个问题最明显：PDD、淘宝联盟、eBay 的商品价格、评分、销量、佣金字段并不完全一致，所以我们要求平台服务先适配成统一的 `ProductCard`，缺失字段必须允许为空。

第二类是路径幻觉。AI 有时会建议修改一个项目里不存在的文件，或者把 Android 代码放到后端目录。后来我们要求它先基于真实目录列修改清单，只能引用仓库里存在的路径。

第三类是业务幻觉。比如图片识别结果不一定有品牌、颜色、材质；搜索结果也不一定每个平台都有评分和销量。如果 AI 按理想数据写死逻辑，真实接口一返回空字段就会出问题。最后我们在筛选、排序和展示逻辑里都补了空值和降级处理。

第四类是过度设计。AI 很容易为了“完整”加抽象、工厂、策略类。我们后来会追问一句：这个抽象解决了什么重复？如果只服务一个场景，就不要新增。

纠偏时，我们会让 AI 把回答拆成“事实、推断、建议、不确定项”。事实必须来自代码或日志，推断要说明依据，不确定项不能包装成结论。这个做法比单纯说“你再检查一下”有效得多。

## 6. 项目中的创新应用案例

### 6.1 异步识别链路

最开始我们想过同步识别：Android 上传图片，后端调用视觉模型，拿到结果后直接返回。AI 分析后提醒我们，这条链路会卡在模型调用和多平台搜索上，移动端等待时间不可控。后来我们改成异步模式：上传后返回 `sessionId`，后端由 `RecognitionOrchestrator` 执行图片处理、模型识别和搜索，Android 通过轮询 `/api/v1/recognition/status/{sessionId}` 或 WebSocket 获取结果。

这个案例里，AI 没有直接替我们写完整代码，但帮我们把同步方案的体验风险提前暴露出来。

### 6.2 多平台搜索降级

VisionCart 要同时检索 PDD、淘宝联盟和 eBay。我们让 AI 帮忙比较串行、并行、缓存和熔断方案，最后保留了 `SearchOrchestrator` 统一编排、`PlatformSearchService` 做平台适配、`PlatformCircuitBreaker` 控制异常平台的设计。这个方案解决了一个实际问题：某个平台失败时，不能让整个比价功能不可用。

后面调试中我们也发现，AI 生成的排序逻辑容易假设字段完整。最后我们用测试和日志压住这个问题：平台结果为空、字段缺失、缓存命中、熔断打开都要有对应分支。

### 6.3 NLP 规则优先，LLM 兜底

自然语言筛选如果完全交给 LLM，成本和不确定性都比较高；如果完全写规则，又覆盖不了复杂表达。我们最后采用规则优先、LLM 兜底：常见价格、平台、颜色、评分、销量、排序走 `RuleBasedNlpParser`，复杂表达再交给 `SpringAiNlpService`。

为了避免模型输出直接影响业务结果，我们又加了三层保护：`PromptSanitizer` 处理提示词注入，`AiOutputValidator` 校验输出字段，`AiTraceService` 记录调用耗时和结果。这个设计让 LLM 成为辅助解析器，而不是直接控制业务逻辑。

### 6.4 Android 与后端联调

Android/后端联调是最容易暴露 AI 生成问题的地方。比如后端使用 `SNAKE_CASE`，Android data class 如果字段对不上，就会出现看似接口成功但页面数据为空的问题。还有 Base URL：模拟器、真机、ADB 转发的地址不同，AI 如果不知道运行环境，很容易给出错误建议。

后来我们联调时会固定给 AI 三类信息：请求定义、后端返回、Android 解析模型。这样它才能判断是 JWT、Base URL、字段命名，还是后端业务逻辑的问题。

## 7. AI 调优实践

我们最后沉淀了几个比较实用的调优习惯。

第一，先让 AI 做 reviewer，再让它做 coder。涉及收藏、价格提醒、搜索排序、NLP 筛选时，先让 AI 指出可能影响的接口、回归风险、安全风险和最小测试集合，再让它写代码。

第二，小步生成。一次只让 AI 处理一个闭环，比如后端 DTO + Controller + 测试，或者 Android ViewModel + UI 状态，不让它同时改后端、Android、数据库和文档。

第三，用真实反馈纠偏。编译错误、测试失败、接口返回、Logcat、后端日志都比口头描述有效。我们不会只说“还是不行”，而是把命令、错误摘要、相关文件和期望结果一起给 AI。

第四，把有效 Prompt 沉淀下来。比如“先列修改文件”“不确定就说不确定”“不要新增依赖”“不要修改接口字段”，这些后来都变成我们反复使用的固定句式。

第五，敏感信息永远不进 AI 输出。当前 IDE 打开了 `.env`，但文档和 Prompt 中只允许出现 `<ARK_API_KEY>` 这类占位符，不能粘贴真实配置。

## 8. 团队收获

做完 VisionCart 后，我们对 AI Coding 的理解从“让 AI 写代码”变成了“用 AI 加速工程闭环”。AI 确实能提高速度，特别是样板代码、测试思路、错误排查和文档整理；但它也会放大上下文缺失带来的问题。

两人团队里，AI 最有价值的用法不是让每个人各自生成一堆代码，而是帮助我们更快对齐：先把需求拆清楚，把边界写清楚，把验收标准写清楚，再由另一个人复核 AI 输出。最后真正保证项目质量的，还是编译、测试、接口联调、日志和人工判断。

如果后续继续优化，我们会重点做三件事：整理常用 Prompt 模板，记录项目里出现过的幻觉案例，补一份 AI 生成代码验收清单。这样 AI Coding 才不是一次性的提效工具，而是可以持续复用的团队开发方法。
